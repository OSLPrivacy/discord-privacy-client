# OSL-RN open questions for owner decision

This note does not decide either question. It presents the choices, costs, failure modes, recovery paths, and evidence needed for an owner decision. OSL-RN remains disabled, is not wired into a send path, and carries no real traffic (`crates/ipc/src/wire_rn.rs:15-17`, `crates/ipc/src/wire_rn.rs:78-83`, `docs/reports/ratchet-lane-2026-07-26.md:7-10`). No option below authorizes real traffic before external cryptographic review (`crates/osl-ratchet-next/MIGRATION.md:406-412`, `crates/ipc/src/wire_rn.rs:78-83`).

## Question 1: When should the downgrade pin be raised?

The owner must choose whether the durable per-peer downgrade floor is raised when this client creates and saves an initiator session after authenticated capabilities report RN support, or only after this client authenticates OSL-RN traffic from the peer. The current initiator creates and saves the session, then raises the pin before peer confirmation only when the caller supplies authenticated capabilities that support RN (`crates/ipc/src/wire_rn.rs:637-668`); successful inbound bootstrap acceptance also saves and raises the pin, but only after authenticated acceptance succeeds (`crates/ipc/src/wire_rn.rs:671-701`). The pin type has no lowering operation (`crates/ipc/src/wire_rn.rs:254-280`), and a pinned peer that does not present verified RN support produces `RnError::PinnedToRn` rather than a v=3 selection (`crates/ipc/src/wire_rn.rs:301-330`). A new peer identity key addresses a different pin, while a client version rollback with the same identity does not reset the pin; no documented recovery procedure exists today (`crates/ipc/src/wire_rn.rs:412-434`, `crates/osl-ratchet-next/MIGRATION.md:157-162`).

### Decision criteria

1. Choose which failure is less acceptable: a silent v3 send after apparent RN support, or a same-identity conversation stranded by an incomplete initiation (`crates/ipc/src/wire_rn.rs:301-330`, `docs/reports/ratchet-lane-2026-07-26.md:315-334`).
2. Define peer confirmation. Successful inbound bootstrap acceptance is authenticated evidence in the responder path (`crates/ipc/src/wire_rn.rs:671-701`). **undetermined:** whether an initiator should confirm on the first successful `receive_rn`, a dedicated authenticated acknowledgement, or another transcript event. A protocol transcript decision and external cryptographic review would settle this; `receive_rn` currently does not raise the pin (`crates/ipc/src/wire_rn.rs:730-750`).
3. Define whether unconfirmed RN state must be quarantined or deleted before any v3 fallback. The migration says an RN session and a stateless v3 wrap must not be mixed in one logical conversation (`crates/osl-ratchet-next/MIGRATION.md:128-132`).
4. Define reset authority separately for provisional and confirmed state. **undetermined:** who can reset, what warning is required, and whether the action is audited. An owner threat-model and product decision would settle this; no lowering operation or documented procedure exists today (`crates/ipc/src/wire_rn.rs:254-280`, `crates/osl-ratchet-next/MIGRATION.md:157-162`).
5. **undetermined:** the rate and causes of initiations that never receive authenticated RN traffic. A pre-production failure-injection and compatibility study, performed without enabling real traffic, would settle whether the availability case is common enough to dominate policy.
6. **undetermined:** capability freshness and the duration of the downgrade window. The current design has no general capability freshness TTL; the costing report says a wire-in needs either fetch-on-send or a documented TTL (`docs/reports/ratchet-wire-in-costing-2026-07-26.md:610-612`). A chosen freshness policy and adversarial timing tests would settle this.
7. Keep the external-review gate independent of the pin decision. The current gate is false and explicitly requires external cryptographic review (`crates/ipc/src/wire_rn.rs:78-83`).

### RECOMMENDATION

Raise the permanent pin only on the first successfully authenticated inbound OSL-RN bootstrap or message, and use a persisted fail-closed provisional state from a local initiation made after authenticated RN-capability evidence until that confirmation. Do not give the provisional state an automatic expiry. Permit an explicit local reset of provisional state only after abandoning the unconfirmed RN session. Keep confirmed pins non-lowerable. This recommendation makes the permanent per-identity claim reflect peer-demonstrated behavior, while the provisional hold prevents capability stripping from silently selecting v3 during the pending interval. Successful inbound bootstrap is already treated as stronger evidence than an advertisement (`crates/ipc/src/wire_rn.rs:671-701`), and the current selector already demonstrates the required fail-closed behavior for a hard floor (`crates/ipc/src/wire_rn.rs:301-330`). This is a recommendation, not a decision, and it does not alter the external-review requirement (`crates/ipc/src/wire_rn.rs:78-83`).

### STRONGEST ARGUMENT AGAINST THIS

The provisional design creates another persisted security state, another crash transition, and a reset surface where the current design has one monotone value and no lowering operation (`crates/ipc/src/wire_rn.rs:254-299`, `crates/ipc/src/wire_rn.rs:588-629`). An attacker who can block the peer's confirmed traffic can keep the conversation unavailable and pressure the user to reset; this follows from the proposed fail-closed provisional behavior. Once the user resets, the same attacker can strip capability and make opportunistic selection return v3 (`crates/ipc/src/wire_rn.rs:325-330`). Legacy v3 has no forward secrecy (`crates/ipc/src/wire_rn.rs:230-236`). The hybrid can therefore turn a protocol downgrade into a user-mediated downgrade while adding state-machine and recovery complexity. If the owner ranks resistance to every post-advertisement downgrade above same-identity availability, the current capability-gated early, non-resettable pin is the stronger and simpler policy (`crates/ipc/src/wire_rn.rs:254-330`, `crates/ipc/src/wire_rn.rs:637-668`).

## Question 2: How should the Discord re-decryption blocker be resolved?

The Discord overlay currently re-opens stored ciphertext in four flows: history rehydration, the control-inbox text drain, attachment listing, and the generic control-inbox drain (`docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-574`). OSL-RN destroys a message key after successful use, so the same ciphertext fails on a second decrypt; that destruction is the forward-secrecy property rather than an incidental implementation detail (`crates/osl-ratchet-next/MIGRATION.md:284-309`). The prepared receive wrapper advances and saves ratchet state before returning plaintext (`crates/ipc/src/wire_rn.rs:730-750`). The owner must therefore choose where replayable application state lives, whether to give up the ratchet's forward-secrecy purpose, or whether to keep the Discord overlay on v3.

| --- | --- | --- | --- | --- |

Cache plaintext or parsed application payload after the first decrypt.** | All four re-open flows must read cached application state instead of reopening the carrier row (`docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-578`). The existing OSL Chats path provides a `persist_user_plaintext` precedent, but Discord still needs explicit behavior for view-once, expiry, burn, attachment metadata, acknowledgements, and revocation rows (`docs/reports/ratchet-wire-in-costing-2026-07-26.md:578`). The implementation must also close the failure window between ratchet-state persistence and cache persistence because the current wrapper saves the advanced session before returning plaintext (`crates/ipc/src/wire_rn.rs:748-750`). **undetermined:** the exact engineering size and whether both durable writes can share an atomic transaction. | **3. Leave the Discord overlay on v3 and use OSL-RN only where ratchet and application state already persist.** | This avoids the Discord re-decryption rewrite. ### Decision criteria

1. Decide whether forward secrecy is required for the Discord overlay. Options 1 and 4 can preserve message-key destruction, option 2 destroys that property, and option 3 leaves the overlay without it (`crates/osl-ratchet-next/MIGRATION.md:270-275`, `docs/reports/ratchet-wire-in-costing-2026-07-26.md:578-584`).
2. Decide whether durable plaintext or parsed content in the encrypted local store is acceptable. The migration document treats acceptance of a plaintext cache as the decisive product question for putting OSL-RN on Discord (`crates/osl-ratchet-next/MIGRATION.md:300-313`, `crates/osl-ratchet-next/MIGRATION.md:406-412`).
3. Define history, self-view of sent messages, view-once, expiry, burn, attachment listing and opening, acknowledgements, revocation deferral, deletion, and retry behavior. The current overlay relies on repeated opens, and self-decryption of sent pairwise RN ciphertext is not available without caching or a second session (`crates/osl-ratchet-next/MIGRATION.md:284-325`, `docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-584`).
4. Require crash-atomicity evidence. A successful RN decrypt advances and saves the session before plaintext returns (`crates/ipc/src/wire_rn.rs:730-750`). A design must show that a crash or downstream write failure cannot consume the only decrypt opportunity without durably recording enough application state.
5. Require failure-injection evidence for all four current re-open flows, including failed deletion, deferred application, attachment list-then-open, and history reruns (`docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-584`, `docs/reports/ratchet-wire-in-costing-2026-07-26.md:182-188`).
6. Treat historical exposure separately from future reversibility. Stopping plaintext caching or key retention later cannot undo copies already persisted, and messages sent under v3 cannot retroactively gain forward secrecy (`crates/osl-ratchet-next/MIGRATION.md:128-134`, `crates/osl-ratchet-next/MIGRATION.md:264-276`, `crates/osl-ratchet-next/MIGRATION.md:300-309`).
7. Keep external cryptographic review as the first gate. The migration places that review before the re-decryption decision and all wire-in work, and the current code gate remains false (`crates/osl-ratchet-next/MIGRATION.md:406-420`, `crates/ipc/src/wire_rn.rs:78-83`).

### RECOMMENDATION

Use option 4 as the target Discord architecture, while leaving the Discord overlay on v3 under option 3 until the ingestion design is complete, crash and failure-injection evidence exists, and OSL-RN has passed external cryptographic review. Do not use option 2. Option 4 addresses the repeated-open data model without retaining consumed message keys. It can avoid permanently conceding forward secrecy for future Discord traffic, but only if the design states exactly what plaintext or parsed content it persists and proves the transition from ratchet advancement to durable application state (`crates/ipc/src/wire_rn.rs:748-750`, `docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-584`). Option 3 is an interim scope boundary, not a claim that Discord has forward secrecy (`crates/osl-ratchet-next/MIGRATION.md:264-276`). This is a recommendation, not a decision, and the gate must remain off pending external review (`crates/ipc/src/wire_rn.rs:78-83`).

### STRONGEST ARGUMENT AGAINST THIS

Option 4 has the largest application-level correctness burden. It does not by itself resolve the plaintext-retention choice. History and attachment listing need durable materialized content somewhere after the only allowed decrypt; this follows from their current repeated-open behavior and the ratchet's one-decrypt rule (`crates/osl-ratchet-next/MIGRATION.md:284-313`, `docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-584`). If the ledger stores full plaintext, option 4 becomes option 1 plus an ingestion subsystem; if it stores too little, users lose history or listing after the consumed key is gone (`crates/osl-ratchet-next/MIGRATION.md:284-313`, `docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-584`). The prepared receive wrapper saves the advanced ratchet before returning plaintext, so a failure before the ingestion result is durable can make the carrier row permanently unreadable (`crates/ipc/src/wire_rn.rs:748-750`). The system already has four distinct repeated-open flows and a deferred-revocation case (`docs/reports/ratchet-wire-in-costing-2026-07-26.md:568-574`, `docs/reports/ratchet-wire-in-costing-2026-07-26.md:182-188`). A new ingestion state machine can therefore create user-visible data loss or failed control processing if its atomicity proof is wrong. Option 1 has an existing `persist_user_plaintext` precedent and a smaller conceptual surface (`docs/reports/ratchet-wire-in-costing-2026-07-26.md:578`). If the owner accepts encrypted local plaintext storage and explicitly redefines view-once, expiry, and burn around it, option 1 may reach the same user-visible result with less implementation risk. If the owner does not accept durable plaintext and does not fund the ingestion proof, option 3 is safer than an incompletely specified option 4, despite leaving the Discord overlay without forward secrecy (`crates/osl-ratchet-next/MIGRATION.md:300-313`, `crates/osl-ratchet-next/MIGRATION.md:264-276`).
