### The subject resolver is the point of the whole lane

Three false greens landed today and all three were one defect: **a harness that guesses its subject
confirms whatever it happened to find.** Selecting "the first process with a window" drove the wrong
lane's application through six UI steps. Every OSL build is titled "OSL Privacy", so a title match
cannot separate two builds.

The countermeasure is structural. A subject exists only via `Resolve-VmqaSubject`, matching
exclusively on the marker window class `<identifier>-sic`. Actuators take a `[VmqaSubject]` as a
mandatory typed parameter, and that type cannot be constructed without the run nonce minted by
`Start-VmqaRun`. There is no overload accepting a pid, title or process name — a caller who wants to
guess has nowhere to put the guess. Two markers for one identifier is `VMQA_AMBIGUOUS_SUBJECT` with
no "pick the newest" tie-break.

**Verified, not assumed**, because PowerShell class methods do not reliably see `$script:` scope
when dot-sourced and the guard would have failed *open*:

```
T1 valid-nonce  -> CONSTRUCTED (expected)
T2 forged-nonce -> BLOCKED: VMQA_BAD_NONCE
T3 direct-ctor  -> BLOCKED: VMQA_BAD_NONCE
T4 stale-nonce  -> BLOCKED: VMQA_BAD_NONCE
```

Getting that took three attempts: the first two returned **exit 0 with no output** because WSL
interop was failing under load. The probe now writes to a file deleted first and freshness-checked,
so a lost stdout cannot masquerade as a pass.

An audit of the agent for `MainWindowTitle`, `Get-Process` and `Select -First` returns **zero hits**.

### The transport had to change, and the new one is better

The design specified Azure Files mounted as `V:` with a storage key from Key Vault. **That is
impossible here.** Both QA storage accounts have `allowSharedKeyAccess=false`, so every key-based
call returns `KeyBasedAuthenticationNotPermitted` and an SMB mount cannot authenticate at all. I
found this by running it, not by reading it.

Transport is now **Azure Blob with Entra ID**: container `vmqa`. The host uses
`az storage --auth-mode login`; the VM agent uses its managed identity to get an IMDS token for
`https://storage.azure.com/` and calls the blob REST API. **There is now no storage key, no SAS and
no Key Vault anywhere in the transport** — strictly better than what was specified. The two crypto
identities were granted `Storage Blob Data Contributor` scoped to the *container*, not the account.
The dead share and the mirrored key secret I had created were removed.

Six cases pass against live Azure: round trip byte-identical, absent → 3, timeout → 4, content
addressing stable, and **torn read → 5 with no file left behind**, which is the property the
two-phase `.ready` protocol exists to provide.

### Four real defects found in review

1. `storage_blob_exists` returned "absent" whenever the az call itself *failed*, converting a broken

2. The storage key was passed as `--account-key` in argv, which is world-readable via `ps aux`.
3. `ensure-share` passed a value to `--fail-on-exist`, a store-true switch — it exited 2 every time.
4. `vmqa-fleet.sh status <typo>` printed an error and **exited 0**, because `expand_target` failing

And one I introduced by specification: in `selftest`, if the negative verdict file was **absent**,
`overall_or_rc` inferred `blocked` from the exit code and the pair could still grade PASS — the
vacuous-pass family one level up. Both halves must now have produced an actual verdict file. A
control that was never measured is not a control.

### Self-test design

One step file for both halves, so they differ only in the `identifier` — structurally true rather
than asserted in a comment. PASS requires **three** things: positive `pass`, negative `blocked`,
**and the positive half having measured something non-empty** (`markerWindowsTotal >= 1`,
`distinctColors >= 16`). Without the third, a rig where nothing runs produces "no marker window" on
both halves and reports success having measured nothing.

A negative control that returns `pass` exits **9**, not 1. That distinction is deliberate: a harness
confirming whatever it finds is worse than a failing one, and an exit code makes it unignorable
where a log line would not.

Verified end to end with no agent running: real requests written to blob, polled, timed out, graded
`INVALID`, exit 1. Every metric extractor defaults so a missing verdict cannot produce a pass.

## The loop is proven

Host → blob → agent → verdict → host, with **no RDP at any point**:

```
overall: pass   diffKey: S1=pass
detail: vmName=OSL-Azure-Client-1; sessionId=1; isInteractiveSession=True
```

**The human RDP step is gone.** The agent is a logon task, so a session must exist; auto-logon is
configured from Key Vault via the VM's managed identity, so the password is read on the VM and
never enters this context. That was the last thing standing between the rig and unattended
operation.

Getting there required granting the crypto pair two things nobody had granted them: `Storage Blob
Data Contributor` scoped to the `vmqa` container, and `Key Vault Secrets User` on the vault — six
other fleet VMs had the latter, the crypto pair did not.

### Seven defects that only existed at runtime

Nothing here was visible by reading. Each was found by running it.

1. **The machine guard rejected its own fleet.** It tested `COMPUTERNAME -notlike 'OSL-*'`, but
   these VMs are named `OSLCLIENT1` — no hyphen. The input-synthesis module refused to load on the
   exact machines it exists to permit. Now guarded on Azure IMDS against a closed allow-list, which
   is also unspoofable off-Azure.
2. **An error handler that destroyed the error.** `Get-HttpStatusCode` dereferenced
   `.Exception.Response`, and under StrictMode a missing property *throws* — so every non-web
   exception became "The property 'Response' cannot be found" and the real fault vanished.
3. **Token cache underflow on the first call.** `DateTime.MinValue.AddMinutes(-5)` is
   un-representable, thrown before a token was ever fetched, so the agent could not make one
   request.
4. **BOM, twice.** Azure returns the List Blobs body BOM-prefixed and `Invoke-WebRequest` hands it
   back as three mis-decoded characters rather than `U+FEFF`, so trimming `U+FEFF` matched nothing.
5. **`[string]` on a `byte[]`** renders decimal byte values, so every sha256 comparison failed and
   legitimate requests graded `torn-request`.
6. **The all-green path was the broken one.** `Where-Object` matching nothing returns `$null`, and
   `$null.Count` throws — so a run where *every* step passed crashed the grader, which is exactly
   why it survived every failing run before it.
7. **The zero-marker case crashed into `blocked`.** A function returning an empty array hands back
   `$null`; the resulting throw surfaced through the generic catch, converting "I could not
   measure" into "the harness positively denied it" — the precise conflation this lane exists to
   prevent. Now: `VMQA_NO_SUBJECT; markerWindowsTotal=0; apparatus-not-proven`.

## Post-report: a critical false green in my own gate, closed

The adversarial review I dispatched to Sol returned ten findings. The first is the one that
mattered, and it was in my acceptance gate rather than in the code under test.

`vmqa-agent.ps1` emits a **real verdict file** with `overall='blocked'` and `steps=[]` when a request
is torn or invalid — a precondition failure, before any step executes. `step_status` then returns
`missing` for every step, and `missing` is not `"pass"`, so the old PASS condition
(`launch_neg != pass && shot_neg != pass`) **accepted it as a good negative control**. A transport
failure on the negative half would have validated the harness. The missing-verdict guard I added
earlier did not help, because this is a genuine verdict file.

`selftest` now additionally requires the negative half to have **executed at least one step** and to
have **passed its own `ping`**. `ping` is the negative half's apparatus check: without it, a blocked
result cannot be distinguished from an agent that was broken on that pass. Both failures exit **9**,
not 1.

Verified against the exact failure shape:

| verdict | old gate | new gate |
|---|---|---|
| `{overall: blocked, steps: []}` | accepted as a good negative control | **rejected, exit 9 (vacuous)** |
| `{ping: pass, launch: blocked}` | accepted | accepted |

So the guard discriminates rather than rejecting everything.

## Post-report 2: input delivery is now measured, not assumed (review finding 6, closed)

`vmqa-win32.ps1:268` discarded `SetForegroundWindow`'s boolean, discarded `SetCursorPos`'s failure,
and the agent returned `pass` unconditionally. So when Windows refuses the foreground transition, or
another window covers or steals focus, the input went to the previous application, **no exception was
raised, and the step passed.**

This is not a hypothetical defect class for this product. OSL's worst known bug is keyboard focus
never reaching the composer, so keystrokes land in Discord and send **plaintext**. A harness that
assumes focus cannot detect the single bug it most needs to detect, and it is the critical path for
the Aug 2 consent-click capture.

What changed:

- `Set-VmqaForeground` now **measures** ownership (`GetForegroundWindow == subject`) with retries and
  returns a boolean instead of discarding one.
- `Invoke-VmqaClick` reads the cursor position back after `SetCursorPos`, and resolves
  `WindowFromPoint → GA_ROOT` to confirm the pixel about to be clicked belongs to the subject rather
  than to something covering it. If any of the three checks fails it **refuses to click**, because a
  click delivered to a covering window is an action against a program nobody chose.
- `Invoke-VmqaType` / `Invoke-VmqaKey` **refuse to send** unless foreground ownership is confirmed
  first, and re-check afterwards in case focus was stolen mid-send. Never send first and verify
  after — by then it is delivered. A single unverified Enter is enough to commit something
  irreversible.
- The agent maps all of these to **`unmeasurable`**, never `pass`: the input did not reach the
  subject, so nothing was learned about how the app responds.

Evidence: both files parse clean under real PowerShell. The delivery checks have **not** been
exercised against a live window yet — the VM is deallocated — so this is `unknown` until a run with a
`click` step happens. It cannot make anything falsely green, because every new path returns
non-`pass`.

## Post-report 3: verdicts are bound to the request that produced them (review finding 2, closed)

`run` permits run-id reuse, so a `runId` match alone does not prove a verdict answers *this*
request — a verdict left by an earlier attempt under the same id would have been graded as the
current result. Freshness at the level of identity rather than time.

The agent already computes the request's sha256 to validate the `.ready` sentinel, so binding it
costs nothing: the verdict now carries `requestSha256`, including on the `blocked` verdicts written
for torn and invalid requests, so even an unparseable request stays attributable. The host computes
the digest of the request it actually sent and **refuses any verdict that does not match**, and also
refuses a verdict carrying no digest at all rather than treating a silent absence as consent.

Proven offline against the case the old check could not catch — all three verdicts carry the **same
matching `runId`**:

| verdict | runId | outcome |
|---|---|---|
| digest matches the sent request | matches | accepted |
| digest of a different request | matches | **refused** |
| no `requestSha256` field | matches | **refused** |

Both files parse clean under real PowerShell. Not yet exercised end to end against the VM (it is
deallocated), so live behaviour is `unknown`; it cannot produce a false green because every new path
refuses rather than accepts.

## Post-report 4: later verbs are bound to the launched process (review finding 5, closed)

`launch` establishes a subject by something stronger than a window class — it starts the process
itself and matches both the pid and the image path. Every **later** verb then re-resolved by class
alone. If the launched process exits and another one carrying the same identifier appears, the run
would change subject mid-flight and keep grading: the wrong-process false green, arriving late
rather than at the start.

`launch` now **pins** the pid it verified, and `Resolve-StepSubject` — the single choke point every
verb resolves through — refuses with `VMQA_SUBJECT_SWAPPED` when a later resolution lands on a
different pid. The swap becomes a hard stop instead of an invisible substitution.

Two scoping details that matter, both of which would otherwise turn this guard into a false red:

- the pin is **cleared per run**, so a pid from a previous run cannot block an unrelated one;
- the pin is **cleared on `launch` entry**, because a run may legitimately launch, kill and
  relaunch — without that, the relaunch resolves a new pid and is blocked for a reason that is not
  a defect.

Evidence: parses clean under real PowerShell; all pin sites confirmed present by inspection. Not
exercised against a live subject swap — the VM is deallocated and I have not manufactured one — so
that is `unknown`. It cannot create a false green: the new path only ever returns `blocked`.

### Open findings after this

`.ready` has no generation invalidation, which fails closed on digest mismatch and is therefore a
diagnosis-quality gap rather than a false-green one.

## Post-report 5: an interrupted run is refused, not replayed (review finding 3, closed)

A run is skipped once a verdict exists. But if the agent died mid-run — crash, restart, reboot — no
verdict was ever written, so the run was re-picked and **every step executed a second time**. Steps
are not all idempotent (`launch` starts a process, and any future verb with a real side effect is
worse), and the re-run could still finish green, so the replay left no trace in the verdict.

The agent now **claims a run before executing any step**, writing `runs/<vm>/<runId>/started.json`
with its own sha, pid and timestamp. If a claim already exists and no verdict does, the run is
refused with `overall=blocked` and `diagnosis='interrupted-run'`.

Refusing is the point. *"Some steps may already have run and I cannot tell which"* is not a
measurement, and quietly redoing them to reach a clean result would be manufacturing the evidence
rather than collecting it.

Checked that this cannot be laundered into a green through the other end: an `interrupted-run`
verdict carries `steps: []`, which the negative-control vacuity guard added earlier rejects with
exit 9 — so an interrupted negative half cannot validate the harness either.

| verdict | steps | ping | selftest outcome |
|---|---|---|---|
| `interrupted-run` | 0 | missing | **rejected, exit 9 (vacuous)** |

Evidence: parses clean under real PowerShell. Not exercised against a real mid-run agent death — I
have not manufactured one — so live behaviour is `unknown`. It cannot create a false green: the new
path only ever writes `blocked`.

### Open findings after this

One, and it is not a false-green risk: `.ready` has no generation invalidation. An overwritten
payload with a surviving older sentinel is caught by the digest mismatch and reported as
`torn-request`, so it fails closed — the gap is that the diagnosis says "torn" when the truer

## Post-report 6: the gate now has a regression test, and mutation testing found a hole in it

Every guard in the acceptance gate was added in response to a real false green, and each was proven
**once**, by a shell one-liner typed by hand and thrown away. Nothing stopped the next edit from
quietly reopening any of them.

`grade_selftest` is now a pure function of two verdict files and their exit codes, and
`scripts/vmqa/test-selftest-grading.sh` drives **that function** with synthetic verdicts. It
deliberately does not reimplement the decision: a test that re-derives the logic is a double
re-asserting whatever its author believed. `vmqa-run.sh` gained a `BASH_SOURCE` guard so sourcing it
does not run `main` — without that the test would have "passed" having tested nothing, and it
refuses to report success on fewer than 11 assertions for the same reason.

**Mutation testing then found that the test itself had a coverage illusion.** Deleting the
empty-steps guard *entirely* still gave 10/10, because a verdict with `steps: []` also has
`ping = "missing"`, so the ping guard produced the same exit 9. The case was asserting an outcome a
**different** guard happened to produce — the same defect family this lane keeps finding elsewhere,
this time in my own test.

Fixed by asserting the **diagnostic** and not only the exit code where guards overlap:

| mutation | before | after |
|---|---|---|
| delete the empty-steps guard | 10/10 pass — **not caught** | **1 failure, caught** |
| delete the positive non-empty assertions | 2 failures, caught | 2 failures, caught |
