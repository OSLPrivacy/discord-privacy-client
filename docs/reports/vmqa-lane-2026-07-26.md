### The subject resolver is the point of the whole lane

Three false greens landed today and all three were one defect: **a harness that guesses its subject
confirms whatever it happened to find.** Selecting "the first process with a window" drove the wrong
lane's application through six UI steps. Every OSL build is titled "OSL Privacy", so a title match
cannot separate two builds.

The countermeasure is structural. A subject exists only via `Resolve-VmqaSubject`, matching
exclusively on the marker window class `<identifier>-sic`. Actuators take a `[VmqaSubject]` as a
mandatory typed parameter, and that type cannot be constructed without the run nonce minted by
`Start-VmqaRun`. There is no overload accepting a pid, title or process name — a caller who wants to
guess has nowhere to put the guess. Two markers for one identifier is `VMQA_AMBIGUOUS_SUBJECT` with
no "pick the newest" tie-break.

**Verified, not assumed**, because PowerShell class methods do not reliably see `$script:` scope
when dot-sourced and the guard would have failed *open*:

```
T1 valid-nonce  -> CONSTRUCTED (expected)
T2 forged-nonce -> BLOCKED: VMQA_BAD_NONCE
T3 direct-ctor  -> BLOCKED: VMQA_BAD_NONCE
T4 stale-nonce  -> BLOCKED: VMQA_BAD_NONCE
```

Getting that took three attempts: the first two returned **exit 0 with no output** because WSL
interop was failing under load. The probe now writes to a file deleted first and freshness-checked,
so a lost stdout cannot masquerade as a pass.

An audit of the agent for `MainWindowTitle`, `Get-Process` and `Select -First` returns **zero hits**.

### The transport had to change, and the new one is better

The design specified Azure Files mounted as `V:` with a storage key from Key Vault. **That is
impossible here.** Both QA storage accounts have `allowSharedKeyAccess=false`, so every key-based
call returns `KeyBasedAuthenticationNotPermitted` and an SMB mount cannot authenticate at all. I
found this by running it, not by reading it.

Transport is now **Azure Blob with Entra ID**: container `vmqa`. The host uses
`az storage --auth-mode login`; the VM agent uses its managed identity to get an IMDS token for
`https://storage.azure.com/` and calls the blob REST API. **There is now no storage key, no SAS and
no Key Vault anywhere in the transport** — strictly better than what was specified. The two crypto
identities were granted `Storage Blob Data Contributor` scoped to the *container*, not the account.
The dead share and the mirrored key secret I had created were removed.

Six cases pass against live Azure: round trip byte-identical, absent → 3, timeout → 4, content
addressing stable, and **torn read → 5 with no file left behind**, which is the property the
two-phase `.ready` protocol exists to provide.

### Four real defects found in review

1. `storage_blob_exists` returned "absent" whenever the az call itself *failed*, converting a broken
   apparatus into a confident "found nothing". Now separates present / absent / query-failed.
2. The storage key was passed as `--account-key` in argv, which is world-readable via `ps aux`.
3. `ensure-share` passed a value to `--fail-on-exist`, a store-true switch — it exited 2 every time.
4. `vmqa-fleet.sh status <typo>` printed an error and **exited 0**, because `expand_target` failing
   inside `$(...)` in a `for` header cannot trip `set -e`.

And one I introduced by specification: in `selftest`, if the negative verdict file was **absent**,
`overall_or_rc` inferred `blocked` from the exit code and the pair could still grade PASS — the
vacuous-pass family one level up. Both halves must now have produced an actual verdict file. A
control that was never measured is not a control.

### Self-test design

One step file for both halves, so they differ only in the `identifier` — structurally true rather
than asserted in a comment. PASS requires **three** things: positive `pass`, negative `blocked`,
**and the positive half having measured something non-empty** (`markerWindowsTotal >= 1`,
`distinctColors >= 16`). Without the third, a rig where nothing runs produces "no marker window" on
both halves and reports success having measured nothing.

A negative control that returns `pass` exits **9**, not 1. That distinction is deliberate: a harness
confirming whatever it finds is worse than a failing one, and an exit code makes it unignorable
where a log line would not.

Verified end to end with no agent running: real requests written to blob, polled, timed out, graded
`INVALID`, exit 1. Every metric extractor defaults so a missing verdict cannot produce a pass.

### Other things now true

- The fleet is **ten** VMs; `OSL-SIGNAL-QA-SCUS` was missing from the doc entirely.
- WARM vs COLD lineages documented with naming enforced in `vmqa-fleet.sh`: a snapshot label must
  start with `WARM-` or `COLD-` or the command refuses.
- Region pinning is **per-disk, verified fleet-specific**: the crypto pair is `centralus`, scrub's
  Independent pair is `northcentralus`. A fleet-wide constant would fail.
- `WARM` is split into `WARM-agent` (no production side effect) and `WARM-identity` (a real,
  not-cleanly-reversible write to the live keyserver), so everything up to the consent boundary
  proceeds without asking anyone.
- The agent writes every file with `UTF8Encoding::new($false)` and never uses `Set-Content` or
  `Out-File`, so it is **BOM-free by construction** — a BOM makes the app's QA trigger fall through
  to the legacy SEND verb, which is irreversible.
- `leak-check` is clean: nothing is running in the subscription.

## The loop is proven

Host → blob → agent → verdict → host, with **no RDP at any point**:

```
overall: pass   diffKey: S1=pass
detail: vmName=OSL-Azure-Client-1; sessionId=1; isInteractiveSession=True
```

**The human RDP step is gone.** The agent is a logon task, so a session must exist; auto-logon is
configured from Key Vault via the VM's managed identity, so the password is read on the VM and
never enters this context. That was the last thing standing between the rig and unattended
operation.

Getting there required granting the crypto pair two things nobody had granted them: `Storage Blob
Data Contributor` scoped to the `vmqa` container, and `Key Vault Secrets User` on the vault — six
other fleet VMs had the latter, the crypto pair did not.

### Seven defects that only existed at runtime

Nothing here was visible by reading. Each was found by running it.

1. **The machine guard rejected its own fleet.** It tested `COMPUTERNAME -notlike 'OSL-*'`, but
   these VMs are named `OSLCLIENT1` — no hyphen. The input-synthesis module refused to load on the
   exact machines it exists to permit. Now guarded on Azure IMDS against a closed allow-list, which
   is also unspoofable off-Azure.
2. **An error handler that destroyed the error.** `Get-HttpStatusCode` dereferenced
   `.Exception.Response`, and under StrictMode a missing property *throws* — so every non-web
   exception became "The property 'Response' cannot be found" and the real fault vanished.
3. **Token cache underflow on the first call.** `DateTime.MinValue.AddMinutes(-5)` is
   un-representable, thrown before a token was ever fetched, so the agent could not make one
   request.
4. **BOM, twice.** Azure returns the List Blobs body BOM-prefixed and `Invoke-WebRequest` hands it
   back as three mis-decoded characters rather than `U+FEFF`, so trimming `U+FEFF` matched nothing.
5. **`[string]` on a `byte[]`** renders decimal byte values, so every sha256 comparison failed and
   legitimate requests graded `torn-request`.
6. **The all-green path was the broken one.** `Where-Object` matching nothing returns `$null`, and
   `$null.Count` throws — so a run where *every* step passed crashed the grader, which is exactly
   why it survived every failing run before it.
7. **The zero-marker case crashed into `blocked`.** A function returning an empty array hands back
   `$null`; the resulting throw surfaced through the generic catch, converting "I could not
   measure" into "the harness positively denied it" — the precise conflation this lane exists to
   prevent. Now: `VMQA_NO_SUBJECT; markerWindowsTotal=0; apparatus-not-proven`.

### A vacuous pass inside my own acceptance gate

An adversarial review dispatched to Sol found that **`shot` never resolved a subject**. It captured
the full desktop and passed on a global distinct-colour count that wallpaper and the taskbar satisfy
alone — so it went green with the application absent, black, covered or minimised. The self-test
leans on `distinctColors` as proof the apparatus measured something, so my own third assertion was
satisfiable without the subject existing. `shot` now resolves the subject first and reports its pid
and window rect. Verified with no app running: `unmeasurable`, not a pass.

Also closed from that review: a verdict must now carry the `runId` that was requested, and
`agent-alive` bounds heartbeat age from below, since a future-dated heartbeat from a stopped agent
would otherwise read as fresh until host time caught up.

## Snapshot state

`OSL-Azure-Client-1-WARM-bootstrap-202607270252`, tagged `lineage=warm-iteration`, `--location`
pinned to `centralus` read from the disk itself.

It is deliberately **not** called `WARM-agent`. It contains the agent, auto-logon and the blob
transport, but **not Discord or the WebView2 runtime**, and `WARM-agent` is defined in
`SETUP-CRYPTO-PAIR.md` as including both. Naming it `WARM-agent` would make the lineage name lie,
which is the one thing the naming rule exists to prevent.

It also **predates store schema v4**, and a v4 database will refuse an older binary. That does not
bite this snapshot — it carries no OSL profile or database at all — but it will bite any
`WARM-identity` taken from it.
