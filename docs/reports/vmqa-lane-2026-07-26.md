## What is built and verified

### The subject resolver — `scripts/vmqa/vmqa-win32.ps1` (committed `924c0ec`)

The harness-integrity core, and the piece I kept in this tab rather than delegating.

Three false greens landed today and all three were one defect: **a harness that guesses its subject
confirms whatever it happened to find.** Selecting "the first process with a window" drove the wrong
lane's application through six UI steps and graded a stale instance. Every OSL build is titled
"OSL Privacy", so a title match cannot separate two builds.

The countermeasure is structural, not advisory:

- A subject can only be produced by `Resolve-VmqaSubject`, which matches **exclusively** on the
  single-instance marker window class `<identifier>-sic`.
- Every actuator takes a `[VmqaSubject]` as a **mandatory typed parameter**. That type cannot be
  constructed without the run nonce minted by `Start-VmqaRun`. There is no overload accepting a pid,
  a title or a process name — a caller who wants to guess has nowhere to put the guess.
- Two markers for one identifier is `VMQA_AMBIGUOUS_SUBJECT`, with **no "pick the newest" tie-break**.
  Quietly choosing one is how a stale instance gets graded.
- Both throws carry `MarkerWindowsTotal`, so a caller can separate a real absence from a dead
  enumerator. Enumeration runs in C# because a throwing PowerShell `EnumWindows` callback truncates
  the sweep silently, manufacturing exactly that conflation.
- Load-time refusal on any machine not named `OSL-*`. That is the whole safety story for a module
  that synthesises real input, so there is no override switch.

**Verified, not assumed.** `ParseFile` returns clean, and the nonce guard was probed in isolation
(without disarming the machine guard on the owner's desktop) because PowerShell class methods do not
reliably see `$script:` scope when dot-sourced — if that failed, the guard would have failed *open*:

```
T0 nonce minted len=32
T1 valid-nonce  -> CONSTRUCTED (expected)
T2 forged-nonce -> BLOCKED (expected): VMQA_BAD_NONCE
T3 direct-ctor  -> BLOCKED (expected): VMQA_BAD_NONCE
T4 stale-nonce  -> BLOCKED (expected): VMQA_BAD_NONCE
```

Getting that result took three attempts. The first two returned **exit 0 with no output** because
WSL→Windows interop was failing under load — a false green of the same family. The probe now writes
to a file that is deleted first and freshness-checked against run start, so a lost stdout cannot
masquerade as a pass.

### The self-test contract — `scripts/vmqa/steps/` (committed `d17043b`)

One step file, not two. The positive run and the negative control share it byte for byte and differ
only in the envelope's `identifier`, so "these runs differ only in the subject" is structurally true
rather than a claim in a comment.

Passing requires **three** assertions, not two:

1. positive half is `pass`;
2. negative half (`org.oslprivacy.doesnotexist`) is `blocked`;
3. the positive half **measured something non-empty** — `markerWindowsTotal >= 1`, `distinctColors >= 16`.

The third is the one that is easy to omit and the one that matters. Without it, a rig where nothing
is running produces "no marker window" on *both* halves, the negative control appears to work, and
the self-test reports success having measured nothing. A negative control that returns `pass` is an
**invalid harness**, not a failing test, and exits `9` rather than `1`.

### The crypto-pair runbook — `scripts/vmqa/SETUP-CRYPTO-PAIR.md` (committed `d17043b`)

Splits WARM into two tiers at the consent boundary:

| Tier | Contains | Production side effect |
|---|---|---|
| `WARM-agent` | WebView2, Discord signed in, agent registered | **none** |
| `WARM-identity` | the above plus an OSL identity | **writes to the live keyserver** |

Creating an OSL identity registers it on the production keyserver and is not cleanly reversible.
Splitting the tiers means everything up to that boundary is buildable with nobody's permission, and
collapsing them would force a production write on every future re-take.
