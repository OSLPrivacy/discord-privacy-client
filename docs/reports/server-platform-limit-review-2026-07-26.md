## MOST LIKELY TO BE REAL

1. **Keyserver `DELETE ... RETURNING` expiry sweep.** It combines every bad scaling dimension Cloudflare documents: one transaction, up to 262,144 deleted rows / 1 GiB, an unbounded returned result accumulated before delivery, and a 128 MB isolate. At maximum legal state it is not merely close to a limit; it is the exact class Cloudflare says must be chunked.
2. **Cipher-store all-at-once blob deletion.** A legal 2 GiB expiry cohort is far beyond Cloudflare's “hundreds of MB” warning, and the retry shape cannot make progress because every tick repeats the same all-or-nothing statement.
3. **Stale multipart ID poisoning reclamation.** The source omits the error handling Cloudflare explicitly requires after `resumeMultipartUpload`. The cross-service crash window is real; only the precise Workers-binding behavior of a second abort remains to be established.

## CHECKED AND SOUND

- **D1 dynamic SQL ceilings:** the repaired attachment metadata delete uses 90 IDs plus one expiry bind (91, below 100) and a sub-1-KB statement. Other runtime-built statements are also small: the control-inbox insert has 12 parameters and the subscription patch has at most 5. No dynamic statement approaches D1's 100,000-byte SQL ceiling.
- **D1 batches:** Cloudflare documents `batch()` as a sequential SQL transaction; a statement error aborts/rolls back the whole sequence. The remaining hazard is not partial SQL commit but completed R2 work followed by Worker termination or D1 failure.
- **D1 database size:** the 8 GiB attachment allowance is R2 object data, not D1 data, so it must not be added to the cipher-store's 2 GiB D1 blob allowance. On Workers Paid, 2 GiB plus metadata/index overhead is below D1's 10 GB decimal ceiling. On Free, D1 is only 500 MB, so the production plan must be verified; the configured 2 GiB blob allowance cannot exist there.
- **D1 rows/results:** individual string/BLOB/table rows are capped at 2,000,000 bytes; scoped payload caps are below that (64 KiB blobs/wrapped shares, 256 KiB links, 16 KiB control bundles). Cloudflare publishes no separate maximum result-row count or serialized-response byte count; Workers CPU/memory govern, which is why the unbounded `RETURNING` row is promoted above.
- **R2 multipart:** 8 MiB non-final parts satisfy the 5 MiB minimum; a short final part is explicitly legal; 65 parts is far below 10,000; all non-final parts are uniform; `Uint8Array` is an accepted `ArrayBufferView` for `uploadPart`.
- **R2 put/delete:** failed conditional `put` preconditions return `null`, matching the direct-upload check. The sweep passes at most 100 keys to bulk delete, below R2's 1,000-key maximum. R2 writes/deletes are strongly consistent after their promises resolve.
- **R2 restart:** reconstructing an active multipart handle from persisted key + upload ID after a Worker restart is supported. The defect is retrying operations without handling the documented possibility that the server-side upload no longer exists.
- **KV sizes/TTL:** keys are far below 512 bytes, values are tiny versus 25 MiB, no metadata is used, and every `expirationTtl` is at least the documented 60 seconds. KV's eventual consistency is acknowledged and mutation-security decisions have moved to D1.
- **Workers ingress/globals:** 26 MiB direct bodies, 8 MiB part bodies, and 1 MiB keyserver mutation bodies are below the lowest account-plan ingress ceiling of 100 MB. Web Crypto (including Ed25519 and `timingSafeEqual`), `atob`/`btoa`, `TextEncoder`/`TextDecoder`, and the other used standards globals exist for the configured 2026 compatibility dates.
- **Cron/subrequests:** Cron wall time is 15 minutes. Paid five-minute Cron CPU is 30 seconds and Paid default subrequests are 10,000; the bounded attachment sweep is below that subrequest ceiling. Free-plan limits are materially lower and incompatible with several configured storage assumptions, so confirm both Workers run on Paid.
- **Cron re-entry outside multipart abort:** SQL expiry predicates are idempotent; D1 batches roll back on statement failure; ready-object R2 delete is idempotent and occurs before D1 metadata removal; payment alerts use a lease. Cloudflare does not document automatic production Cron retry/overlap behavior, but the next scheduled tick safely re-enters these paths except for the stale multipart case above.
