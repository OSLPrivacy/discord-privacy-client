HIGHEST RISK

1. `cipher-store-cf/test/attachment-r2.test.ts:27` and `cipher-store-cf/test/helpers/d1.ts:141`: the R2 `put()` doubles still accept unknown-length streams and ignore `onlyIf`. This is the exact outage class: production rejected the real request while the double accepted it. The source now guards by passing `Uint8Array`, but the double remains permissive.
2. `cipher-store-cf/test/attachment-r2.test.ts:293` and `cipher-store-cf/test/helpers/d1.ts:108`: multipart `uploadPart()` doubles accept arbitrary streams and do not enforce real multipart constraints. This is the second half of the same R2 class and would hide a regression in part upload.
3. `cipher-store-cf/package.json:95`: cipher-store's plain Node runner cannot execute workerd-only globals. I found no active `FixedLengthStream`/`HTMLRewriter`/`caches` use, which is good, but this is the highest-value category because one workerd-vs-Node split already hid a production-wide failure.
4. `cipher-store-cf/test/link-grant.test.ts:53`: link-grant replay suppression is a KV Map fake around a security decision. Production KV is eventually consistent and not atomic; exact concurrent grant replays could be over-admitted unless protected elsewhere.
5. `cipher-store-cf/test/helpers/d1.ts:78` and `cipher-store-cf/test/attachment-r2.test.ts:316`: D1 `batch()` atomicity is not modeled. The source uses `batch()` during attachment completion, where partial metadata transitions are exactly the kind of crash/retry state tests are meant to prove.

It would close most D1/runtime-global gaps: `cipher-store-cf/test/attachment-r2.test.ts:48`, `cipher-store-cf/test/attachment-r2.test.ts:316`, `cipher-store-cf/test/helpers/d1.ts:78`, `cipher-store-cf/test/helpers/d1.ts:24`, `cipher-store-cf/test/helpers/d1.ts:57`, `cipher-store-cf/test/link-lane.test.ts:43`, `cipher-store-cf/test/blob-bounds.test.ts:123`, and the Node/global split at `cipher-store-cf/package.json:95` if the tests execute through the worker-pool environment with actual workerd APIs.
