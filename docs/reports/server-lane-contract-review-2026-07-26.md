# Adversarial design review of the two implementation contracts

Verdict: neither contract is safe to hand to an implementation team as written. Contract 1 contains two cryptographic/protocol contradictions that would preserve the hostile-recipient delete attack. Contract 2 has the right trust anchor idea, but its rollout leaves the new namespace open to the same first-claim attack, its rotation proof is underspecified, and its description of migration 0029 is factually wrong.

## CONTRACT 1 — scope-wide prose-token delete capability

### Concrete flaws

| Severity | What breaks | Concrete scenario |
|---|---|---|
| **CRITICAL** | Step 3's fetch/delete separation is not an authority separation. Distinct domain labels prevent cross-protocol collisions; they do not hide a derived value from a holder of the parent key. | The contract says to derive `fetch` and `delete` “from the same secret” and give recipients only `fetch` (`docs/reports/server-lane-2026-07-26.md:491-493`). A recipient who holds that shared conversation secret can run the public delete-label KDF itself. The current design explicitly gives both sides the same `mac_key` (`crates/ipc/src/prose_token.rs:97-107`, with DM symmetry asserted at `:408-433`). Per-recipient fetch authority and sender-only delete authority must come from different roots, or delete must be an independent random capability known only to the sender. |
| **CRITICAL** | Step 2 cannot be implemented against the present upload protocol. | The client must send the fetch token in the upload POST before it has a response (`crates/ipc/src/cipher_store_client.rs:320-327`). The Worker generates the ID during that request and returns it afterward (`cipher-store-cf/src/endpoints/blob.ts:100-133`); the client parses it only at `crates/ipc/src/cipher_store_client.rs:339-357`. This is exactly why `prose_token_send` uses the all-zero placeholder before upload and learns `id_hex` later (`crates/ipc/src/prose_token.rs:194-224`). “Replace the placeholder with the blob id” is impossible without client-chosen IDs, a reserve/finalize protocol, or a separate post-allocation capability-setting operation. |
| **HIGH** | Per-blob derivation alone only raises the attack cost; it does not stop the stated attacker. | A channel member can decode the cover to the eight-byte ID (`crates/ipc/src/prose_token.rs:273-278`). If that member also has the shared derivation root, it computes the target's per-blob delete value. The change turns one scope-wide computation into one computation per observed cover—roughly O(1) extra work per victim message. Per-blob binding is useful blast-radius control only after delete authority is genuinely sender-exclusive. |
| **CRITICAL** | “Per-conversation secret state” is not a complete multi-recipient key contract. | `derive_scope_primitives` currently takes only `ScopeInput`, deliberately constructs a symmetric value from public scope metadata, and contains special DM fallback behavior (`crates/ipc/src/prose_token.rs:84-133`). Pairwise ratchet roots are not one group-wide secret. The contract does not define the source for GC/server scopes, membership add/remove rekey, epoch retention for old covers, multiple sender devices, or how every intended recipient gets fetch authority while a hostile member does not get delete authority. An implementation team can make incompatible, individually plausible choices here. |
| **CRITICAL** | Client-first/server-second sequencing is unsafe and cannot realize the split on the current schema. | The old Worker stores one `fetch_token` on upload (`cipher-store-cf/src/endpoints/blob.ts:112-129`) and checks that same field for GET (`:192-218`) and DELETE (`:274-291`). If a new client puts recipient fetch authority there, recipients still delete. If it puts sender-only authority there, recipients cannot fetch. An extra delete header sent to an old Worker is ignored and never persisted. The report recognizes that client-only work is not the fix (`docs/reports/server-lane-2026-07-26.md:503-506`) but contradicts that by sequencing the server change after it (`:494-498`). |
| **CRITICAL** | The proposed rollout has no safe rollback boundary. | Once new clients emit a second capability, rollback to today's Worker silently discards it and resumes authorizing DELETE with `fetch_token` (`cipher-store-cf/src/endpoints/blob.ts:274-291`). A rollback after client emission therefore reopens hostile-recipient deletion for new messages. “Ship together” is not a deploy or rollback procedure. |
| **HIGH** | Step 5 calls a still-vulnerable legacy policy “safe” and misses the safe fail-closed migration. | Today a row with `fetch_token = NULL` is deleted without any authorization (`cipher-store-cf/src/endpoints/blob.ts:271-293`). Keeping old behavior preserves the exact attack for up to seven days. It is correct that the server cannot manufacture an author-only secret: legacy rows contain no author identity and copying/deriving from the shared fetch token preserves the defect. The safe migration is to reject DELETE when the new delete digest is absent while leaving legacy FETCH intact until TTL expiry. That temporarily removes legitimate remote burn for legacy rows; it does not leave them attacker-deletable. |
| **HIGH** | Author-only capability persistence and multi-device recovery are absent. | The current encrypted ledger stores only blob IDs because the delete token can be rederived (`crates/ipc/src/scope_blobs_file.rs:25-33`, `:60-74`). The production burn path walks that local ledger and retries failed IDs (`apps/osl-hub/src/security.rs:2055-2067`). With a random or sender-only delete capability, an originating-device loss, reinstall, or second author device cannot burn the blob unless the capability is included in encrypted recovery/sync state. The send failure-cleanup path also needs the capability immediately after upload (`apps/osl-hub/src/broker.rs:1362-1383`). |
| **HIGH** | Step 4 is materially larger than “one line each,” leaving wire incompatibilities unspecified. | A real v2 path needs a second header and parser, schema and capability-scheme marker, digest-at-rest rules, upload binds, a changed Rust client API, distinct DELETE status/header semantics, conditional deletion, legacy rules, and compatibility tests. Current upload sends exactly one capability (`crates/ipc/src/cipher_store_client.rs:320-327`) and the Worker inserts exactly one capability field (`cipher-store-cf/src/endpoints/blob.ts:112-129`). |
| **MEDIUM** | “Delete the blob” is only the unfetched-recipient portion of multi-recipient burn. | The hub explicitly says server deletion prevents peers who have not fetched from fetching, then queues revocations for peers who already fetched (`apps/osl-hub/src/security.rs:2070-2083`). An implementation must not turn successful server DELETE into a claim that already-fetched recipient copies were erased. |

### WHAT I WOULD CHANGE

Replace the five steps with the following wording:

1. **Separate the deletion fix from the group-key redesign.** “For every upload, generate an independent random 32-byte `delete_cap` before the POST. It is sender authority and MUST NOT be derived from any key possessed by a recipient. Send it in `X-OSL-Delete-Token`; store only `SHA-256(delete_cap)` with the row. Row association is the per-blob binding. A recipient fetch key and a sender delete key may use domain labels only when their parent roots are already held by different principals.”

2. **Do not claim blob-ID KDF binding on the current one-request protocol.** “The deletion fix does not need the server-generated ID as KDF input. If deterministic per-blob fetch tokens remain a goal, first define either (a) client-chosen random IDs with collision-safe no-overwrite/retry semantics or (b) reserve-ID plus one-time-authorized finalize. Only then may a capability be derived over the allocated ID. Never specify an input that is unavailable when the request must send the output.”

3. **Deploy a compatibility Worker before any client emits.** “Migration adds `capability_scheme` and nullable `delete_token_sha256_hex`. Worker v2 accepts old one-capability uploads and new two-capability uploads. GET continues to verify only fetch authority. DELETE for a v2 row verifies only `X-OSL-Delete-Token`; it MUST NOT accept the fetch token. Use an atomic conditional delete. Preserve actionable semantics: 204 when deleted or already absent, 401 when the header is missing, and 403 when a still-existing row has a mismatched capability, so a legitimate client never clears its retry ledger after a false-success response.”

4. **Make legacy DELETE fail closed.** “A row with no delete digest remains fetchable under its existing fetch rule but is not remotely deletable. Do not backfill a delete digest from `fetch_token`, scope metadata, or any other shared value. Such rows TTL out in at most seven days. This deliberately trades legacy remote-burn availability for integrity; preserving both is impossible because no authorship proof was stored.”

5. **Ship and persist client authority.** “Client v2 sends the random delete capability, receives the server ID, and atomically records `(scope, blob_id, delete_cap, expiry)` in encrypted recoverable state before publishing the cover. Failed persistence triggers deletion with that capability and retains a retry record if cleanup fails. Define encrypted multi-device transfer/sync or explicitly state that only the originating author device can remotely burn.”

6. **Close emission with an explicit compatibility boundary.** “After v2 adoption, reject new uploads that omit the delete capability, or continue accepting them only as undeletable legacy rows. The former necessarily fails closed for old senders; the latter preserves sending but not remote burn. Do not claim both complete enforcement and compatibility with clients that never shipped. Once clients emit v2, rollback is permitted only to a Worker version that persists and enforces v2 delete digests.”

7. **State multi-recipient semantics.** “One author's delete capability removes the shared server object for all recipients who have not fetched it. Recipients do not receive unilateral authority to delete another author's server object; their burn is local plus an authenticated revocation/notice path. Already-fetched copies remain outside unilateral server erasure.”

If the team still wants secret-authenticated covers/fetch, add a separate prerequisite contract that defines DM and group key distribution, membership epochs, removal, retained read epochs, multi-device recovery, and version negotiation. “Use per-conversation secret state” is not enough for that work.

### WHAT IS SOUND AS WRITTEN

- The defect diagnosis is correct. HKDF currently has no secret input (`crates/ipc/src/prose_token.rs:19-26`, `:97-107`), upload uses the all-zero placeholder (`:194-218`), burn rederives that same value (`:338-347`), and Worker DELETE compares it as the sole authorization (`cipher-store-cf/src/endpoints/blob.ts:274-291`).
- “Public scope ids may remain as domain separation, never as sole entropy” is correct (`docs/reports/server-lane-2026-07-26.md:486-488`).
- Per-object separation is worthwhile once authority is actually separated. Compromise of one concrete capability should not authorize other rows. It is blast-radius control, not the primary authorization fix.
- Splitting fetch from delete is the correct goal. The correction is that different labels under a shared parent secret do not create different holders.
- Author-only server deletion matches the current ledger's actual intent: it records blobs “this client has uploaded” and burns those (`crates/ipc/src/scope_blobs_file.rs:1-13`). A sender can still burn one group message for every unfetched recipient. What disappears—and should disappear to close this attack—is a recipient's ability to globally delete another sender's object.
- “Do not backfill a derived value” is correct because no author-exclusive provenance exists in legacy server state. What is wrong is retaining permissive legacy DELETE instead of disabling it.
- The seven-day maximum legacy lifetime is correctly bounded by the allowed TTL set (`cipher-store-cf/src/endpoints/blob.ts:21-27`, `:66-73`). That bounds exposure; it does not make the exposure safe.
- The report correctly says steps 1–3 alone are not a full fix (`docs/reports/server-lane-2026-07-26.md:503-506`). Server enforcement is indispensable.

## CONTRACT 2 — open-registration residual

### Concrete flaws

| Severity | What breaks | Concrete scenario |
|---|---|---|
| **CRITICAL** | Deploy 1 does not reserve the derived-ID namespace, so the first-claim attack survives the rollout. | “Accepts both schemes and records which” allows an attacker to submit Bob's 32-character future derived ID without root fields as a scheme-0 registration. The server currently accepts every bounded, non-snowflake string (`keyserver-cf/src/endpoints/register.ts:110-116`) and Case A proves only control of the attacker's submitted operational key before insertion (`:190-202`). Bob's later scheme-1 registration collides with the attacker's row. A reserved, syntactically disjoint prefix must reject legacy claims from the first server deploy. |
| **CRITICAL** | The final deploy is necessarily fail-closed for a client that has not shipped, contrary to Step 6. | A current client emits only the existing request (`crates/keystore/src/client.rs:599-625`). “Server refuses scheme 0” must reject a never-upgraded first launch; if applied to existing refresh/rotation, it disables installed identities too. The endpoint is deliberately hit on steady-state re-registration (`keyserver-cf/src/endpoints/register.ts:217-220`). No ordering makes enforcement compatible with a client that never learned the protocol. The contract needs an adoption/minimum-version gate and must distinguish new Case A registration from authenticated operations on existing legacy rows. |
| **HIGH** | Once clients emit derived IDs, rollback to today's Worker reopens the vulnerability for those IDs. | The current Worker ignores unknown JSON fields, reconstructs only the old signed bundle (`keyserver-cf/src/endpoints/register.ts:128-186`), and accepts the asserted ID after operational-key proof (`:190-202`). A root-capable client talking to that rollback target does not get root enforcement. The rollout needs a point of no return: after client emission, rollback may only target a server version that reserves and verifies the new namespace. |
| **CRITICAL** | Step 3 is too ambiguous to preserve rotation replay/CAS safety. | Today rotation requires the submitted previous key to equal the stored current key, verifies its signature (`keyserver-cf/src/endpoints/register.ts:298-333`), verifies possession of the new key (`:335-342`), and CAS-updates against the old key (`:364-370`). “Root signs the canonical bundle” does not say root proof is additive, define distinct operation domains, include the stored previous key or generation, or prohibit replay. An implementation that treats a root-signed bundle as sufficient can replay an old root-signed bundle to roll back a newer operational key. The Rust client documents the existing old-key/new-key dual proof at `crates/keystore/src/client.rs:628-674`. |
| **HIGH** | A forever-valid online root is an unrevocable account credential after compromise. | Recovery entropy currently rederives every key (`crates/keystore/src/identity.rs:236-283`), so phrase compromise already compromises an unrotated identity. But current rotation gates later changes on the currently stored signing key (`keyserver-cf/src/endpoints/register.ts:310-333`). If an immutable root authorizes every future rotation, theft of the phrase/root remains useful forever even after operational-key rotation. The contract has no root epoch, successor/revocation protocol, recovery override rules, or explicit statement that root compromise requires a new identity. A self-certifying stable ID needs an immutable anchor, but that does not require the anchor secret to remain an unrestricted, forever-online rotation credential. |
| **HIGH** | Root-signing every routine registration/rotation unnecessarily exposes the highest-value credential and changes the existing rotation trust model. | Step 3 requires the root signature on both operations (`docs/reports/server-lane-2026-07-26.md:806-808`). That means the secret derived from the recovery phrase must be available for ordinary online mutations. Existing normal rotation already has old-key authorization, new-key possession, and CAS (`keyserver-cf/src/endpoints/register.ts:327-370`). Root proof should be required for first enrollment and a separately specified recovery/root-rotation path; making it a routine co-signer needs an explicit threat model and lifecycle. |
| **MEDIUM** | Publishing the same raw root is a permanent cross-context correlator; hashing it with a domain does not solve that. | `H(domain || root_pub)` domain-separates the ID, but every registration/rotation also carries the identical `root_pub`. Two deployments or protocols can join records on the raw key even if their ID domains differ. Within one keyserver the stable ID is already a correlator, so this is not an additional same-service leak; across services/environments it is. Derive a keyserver-namespace-specific child root from the recovery entropy and prohibit its reuse elsewhere. Current recovery entropy is sealed and documented “never transmitted” (`crates/keystore/src/identity.rs:82-94`), so publishing a permanent root is a new privacy/lifecycle decision, not something that “already exists” merely because the entropy exists. |
| **MEDIUM** | The 160-bit security rationale overstates the effective strength and omits generic collision strength. | Twenty bytes do encode to exactly 32 unpadded base32 characters. They give 160-bit targeted second-preimage work but only about 80-bit generic collision work. More importantly, the root is derived from exactly 128 bits of recovery entropy (`crates/keystore/src/identity.rs:82-94`, `:187-191`), so credential search cannot honestly exceed that 128-bit source. Targeted pre-registration remains adequately hard, but “160 bits because second-preimage resistance” is incomplete. Because the friend-code parser already permits IDs up to 160 characters (`apps/osl-hub/src/security.rs:2982-2988`) and the server permits 256 UTF-8 bytes (`keyserver-cf/src/lib/validation.ts:18-25`), full SHA-256 base32 is feasible unless a separately measured carrier budget says otherwise. |
| **HIGH** | The encoding is not exact enough for an implementation contract. | “base32” could mean RFC 4648, Crockford, or z-base-32. `[0..20]` is language-dependent notation. The contract lacks an ID prefix, exact domain bytes/framing, raw-root length and decoding rule, canonical regex, root-signature domains, bundle framing, and a known-answer vector. Existing registration deliberately mirrors a byte-exact client/server encoder and test vector (`keyserver-cf/src/lib/signed-request.ts:10-22`, `:82-149`). Without the same precision here, two teams can implement incompatible but reasonable versions. |
| **HIGH** | Step 5's description of migration 0029 is factually wrong. | Migration 0029 explicitly says a non-platform identity may re-register with its current key to enable lookup (`keyserver-cf/migrations/0029_authoritative_osl_identity.sql:3-7`). Case B calls `enableIdentityLookup` (`keyserver-cf/src/endpoints/register.ts:205-214`), which flips the row to enabled (`keyserver-cf/src/lib/db.ts:399-415`). New Case A registrations are inserted enabled (`keyserver-cf/src/lib/db.ts:103-128`), and rotation also sets enabled (`:138-170`). Legacy rows are not “permanently unable to enable lookup” today. Every one of those branches must become scheme-aware; merely adding `identity_scheme` does not quarantine them. |
| **HIGH** | Permanently stranding every legacy identity is unnecessary, and no actual recovery path is specified. | A holder of the stored legacy operational key can sign a transition to a new derived ID, while the new root signs the same transition. The server can verify `new_id = H(new_root)` and migrate to a namespace the legacy holder could not choose independently. A squatter can migrate only its own old key to an ID derived from its own root; it cannot preserve a claim on Bob's derived ID. Seed-backed identities have recovery entropy (`crates/keystore/src/identity.rs:181-191`); old loaded identities may have `None` (`:82-87`, `:121-144`) and need newly created recovery material or full re-onboarding. Foreign-key/data movement makes migration nontrivial, but not cryptographically unsound. |
| **HIGH** | The contract ignores the current emitted identifier and duplicate implementation sites. | Current `native_user_id` hashes the operational Ed25519 and X25519 public keys, truncates to 20 bytes, and emits `osl_` plus hex (`crates/keystore/src/identity.rs:194-224`). The hub has a second implementation with the same behavior (`apps/osl-hub/src/password_lifecycle.rs:339-351`). An implementation team following only “derive a root” can leave one path emitting the old rotatable-key ID. The contract must name every generation/import/migration path and require one shared canonical function plus cross-language vectors. |
| **MEDIUM** | Scheme must be inferred from validated proof, never trusted from a request flag. | “Records which” does not say how (`docs/reports/server-lane-2026-07-26.md:818-820`). If `identity_scheme = 1` is accepted from JSON before root decoding, ID recomputation, root-signature verification, and exact-root persistence, an attacker can bless a legacy claim as derived. |

### WHAT I WOULD CHANGE

Replace the six steps with:

1. **Define the root and its limits.** “Derive a keyserver-namespace-specific Ed25519 root from the 16-byte recovery entropy with a byte-exact HKDF label such as `OSL/keyserver/identity-root/v1`; publish only its canonical 32-byte public key. Do not reuse this raw root across environments or protocols. The root proves first enrollment. It MUST NOT replace current-operational-key authorization, new-key possession, or CAS. Before using it as a recovery/rotation authority, separately define root epochs, successor/revocation, replay protection, and compromise behavior. If no such protocol ships, root compromise requires re-onboarding under a new identity.”

2. **Make the identifier namespace syntactically reserved and byte-exact.** “Define `user_id = "osl1_" || rfc4648-base32-lower-no-pad(SHA-256(UTF8("OSL-ID-v1\\0") || root_pub_32))`, using the full 32-byte digest unless a measured carrier limit justifies truncation. Enforce exact lowercase canonical text and publish mirrored Rust/TypeScript known-answer vectors. If the 20-byte form is retained, say `first 20 digest bytes`, document 160-bit targeted/80-bit generic collision strength and the 128-bit recovery-entropy ceiling. A 20-byte digest is exactly 32 unpadded base32 characters and is acceptable for targeted anti-squatting; it is not a full 160-bit collision claim.”

3. **Specify enrollment and rotation proofs separately.** “Case A verifies (a) the existing operational-key REG proof, (b) a distinct `OSL-ROOT-ENROLL-v1` signature by the submitted root, and (c) exact recomputation of the reserved ID. Persist the exact 32-byte root. Ordinary Case C retains stored-previous-key equality, previous-key signature, new-key possession, and SQL CAS; the submitted root must byte-equal the stored root. A root-authorized recovery or root change is a different operation with a distinct domain, stored monotonic epoch/server challenge, successor key, and CAS. Canonical root messages use unambiguous length-prefixed decoded bytes and cover operation, scheme, user ID, root bytes, previous current key/epoch, complete new bundle, and capability bitmap.”

4. **First server deploy reserves and enforces the namespace.** “Add `identity_scheme`, `ik_root_ed25519_pub`, and any required root epoch. Infer scheme server-side only after full proof validation. From this deploy onward, an `osl1_...` Case A request is accepted only as scheme 1 with a valid root proof and exact recomputed ID; missing or invalid root proof is rejected and can never be recorded as scheme 0. Existing scheme-1 operations compare the submitted root to the stored bytes. Existing scheme-0 rows cannot be promoted by flipping a flag.”

5. **Provide a real legacy transition.** “Remove unconditional scheme-0 lookup re-enable behavior. Offer an idempotent dual-signed migration in which the currently stored legacy Ed key and the new root sign a length-prefixed statement containing `(old_id, new_id, new_root, complete bundle, server challenge/epoch)`. Verify the derived `new_id`, create/move the scheme-1 account and all owned keyserver rows atomically, and leave the old ID non-resolving or tombstoned—never as a lookup alias. A legacy claimant can move only to its own derived identity, so this does not let it claim another person's derived ID. Peers consume a signed continuity statement but retain the safety-number ceremony. If the old current secret is unavailable, no cryptographic continuity proof exists and re-onboarding is required.”

6. **Use an honest rollout and rollback contract.** “Deploy A: server fully validates scheme 1, reserves `osl1_`, and continues authenticated operations plus migration for existing scheme 0. Deploy B: clients create scheme-1 identities, can read both schemes, and ship explicit legacy migration UX. Deploy C occurs only after a measured minimum-version/adoption gate: reject new scheme-0 Case A registration while retaining only the bounded legacy operations needed to migrate existing rows. Old first-launch clients will fail after C; state this unavoidable boundary. Once B emits `osl1_` IDs, rollback is permitted only to a build that still reserves that namespace and validates the root.”

7. **State the privacy and compromise model.** “The stable ID and enrolled root are permanent within this keyserver namespace and are correlators there. A key-derived ID proves control of a root, not personhood. Safety-number/friend-code verification remains the human binding. Compromise of the sole current root cannot be distinguished cryptographically from its owner; recovery from that event requires a previously specified successor/recovery factor or a new identity.”

### WHAT IS SOUND AS WRITTEN

- The residual diagnosis is correct. The server validates only bounded form plus snowflake exclusion (`keyserver-cf/src/endpoints/register.ts:110-116`); first registration proves control of the submitted key, not entitlement to the asserted ID (`:190-202`).
- The rotatable-key trap is real. Current rotation preserves `user_id` while changing the full operational bundle (`keyserver-cf/src/endpoints/register.ts:315-370`), and the Rust client explicitly takes the ID from the old identity (`crates/keystore/src/client.rs:628-646`). Deriving the stable ID from the current operational key would change identity on rotation.
- A distinct stable key is derivable for seed-backed identities. Current identity generation draws 16 bytes and deterministically derives labeled keypairs (`crates/keystore/src/identity.rs:181-191`, `:227-283`). A separate, exact derivation label is the right primitive. What does not follow is that publishing and lifecycle of that root have already been designed.
- Server recomputation is the core anti-squatting fix. Once the namespace is reserved, root proof is verified, and exact root bytes are persisted, the server no longer trusts a caller-asserted derived ID.
- The proposed 20-byte/base32 arithmetic is correct: 160 bits produce exactly 32 unpadded base32 characters. A fixed 32-character base32 value cannot match the 17–20 decimal-digit snowflake predicate (`keyserver-cf/src/lib/validation.ts:28-30`), even in the vanishing case that every base32 symbol happens to be a digit. The real namespace collision is with arbitrary legacy opaque IDs, not with snowflakes.
- Lowercase/no-padding and domain separation are good canonical choices once the precise alphabet, bytes, framing, prefix, and test vector are specified.
- The three-phase dependency shape—compatible server, emitting client, enforcement server—is directionally right. It needs namespace reservation in phase A, an adoption gate, and a non-regressing rollback floor.
- Refusing to mark an existing caller-chosen ID as fully key-derived merely because it already exists is correct. A transition must move to a recomputed derived ID; “grandfathering” the old string as scheme 1 would preserve the original assertion.
- The human-identity caveat is exactly right (`docs/reports/server-lane-2026-07-26.md:822-824`). A self-certifying identifier binds a key to a label, not a key to a person, and does not replace the safety-number ceremony.
