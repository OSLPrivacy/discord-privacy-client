# Signal Desktop native QA contract

This lane integrates only the official installed Signal Desktop application. It
does not use a browser route, inject code, read Signal storage, inspect databases,
extract tokens, or infer account state from private runtime data.

## Window claim

The native host may claim an existing linked session only when all of these hold:

- fixed application ID `signal`;
- canonical executable path `%LOCALAPPDATA%\Programs\signal-desktop\Signal.exe`;
- Authenticode publisher exactly matches the reviewed Signal allowlist;
- exactly one visible top-level `Chrome_WidgetWin_1` titled exactly `Signal`;
- executable path, Windows session, PID, process creation time, retained process
  handle, and HWND remain consistent at every operation;
- the receipt says `existingNativeCompanion` and `captureProtected: false`.

The host never creates a secondary Signal profile, kills Signal, reads its profile,
or claims that a borrowed foreign window inherits OSL screenshot protection.

## Protected destination gate

Opening the native window is not permission to send an OSL-protected message.
Protected send remains unavailable until a provider-specific accessibility adapter
simultaneously proves:

1. one exact claimed Signal window and renderer accessibility root;
2. one selected conversation, bound to a stable OSL-side opaque digest;
3. the exact visible participant set and direct/group conversation kind;
4. one enabled visible composition textbox geometrically inside that conversation;
5. a fresh generation token covering window, account, conversation, participants,
   composer, and OSL owner identity;
6. the same facts immediately before carrier placement and immediately after send.

Any ambiguity, stale element, relink screen, update screen, call surface, modal,
conversation switch, participant change, or missing accessibility fact invalidates
the generation and fails closed. A QA shortcut may remove navigation clicks but may
not mint or bypass this proof.

## Public-source evidence

Public Signal Desktop source at commit
`286ac81b7d07005757124eebad2cea3d7e26224a` provides useful accessibility hints:

- conversation rows expose a localized `ConversationList__aria-label` beginning
  with `Chat with {title}`;
- the composition wrapper exposes `data-testid="CompositionInput"` and an enabled
  state, while the actual editor is generated by Quill;
- the visible conversation title is rendered by `ConversationHeader`.

These are research hints, not sufficient runtime proof. DOM test IDs and CSS class
names are not assumed to appear in Windows UI Automation. Exact selectors and
geometry must be established against the signed installed build without reading
message content or private Signal state.

## Live QA logging

Receipts may contain only bounded semantic enums, hashes, booleans, counts, geometry,
versions, timestamps, and invocation IDs. They must not contain phone numbers,
contact names, conversation titles, message text, QR data, credentials, attachment
contents, Signal paths beyond the fixed allowlisted executable, or private profile
metadata.

## First-run OSL bootstrap

A clean QA VM creates a disposable local OSL identity. The manifest contains
only one bootstrap Key Vault reference per VM: the OSL primary password. The
VM's system-assigned managed identity reads it. A one-shot named pipe transfers
the bounded UTF-8 password into a limited interactive scheduled task; the
wrapper fills OSL's exact create-password and confirmation controls and clears
its byte array. No recovery phrase is required, extracted, imported, or stored.

The wrapper must never read, enumerate, or serialize recovery-page text. It
proves success only through the presence of the fixed `recovery-continue`
AutomationId; the immutable deploy loop immediately relaunches OSL instead of
continuing through that page. A profile that already exposes either the unlock
gate or workspace is reported as `profileAlreadyPresent` and is not replaced.
Missing or ambiguous controls, partial profiles, wrong hashes, wrong sessions,
rejected creation, and unknown UI states fail closed. Signal linking material is
never accepted by this path.

## Immutable deployment loop

The one-command preparation sequence is ordered as follows:

1. deploy pinned OSL and WebView2 artifacts while preserving the exact Signal
   PID set and all configured profile roots;
2. audit the installed hashes, Signal hash/publisher, session owner, and exact
   processes;
3. create a disposable identity only in an empty OSL profile;
4. redeploy the same immutable artifacts so fresh identity creation leaves the recovery
   page through a pinned process relaunch, then audit and unlock;
5. inventory and claim the exact window, then produce a redacted
   OSL-titlebar-only screenshot.

For a new VM, both configured OSL artifacts must be absent and the install
directory must already exist. The tool moves in only the two verified downloads,
starts exactly one primary, and removes those new files if launch fails. If
either artifact already exists, both must exist and exactly one matching primary
process must be running before backup/replace. Neither path deletes, seeds, or
copies an OSL profile.

Every stage runs on both dedicated Signal aliases. A failure writes a bounded
terminal receipt with no raw Azure output. Live message tests do not begin from
a partially prepared pair.

## Complete live matrix

The controller owns a fixed matrix so a manifest cannot omit a direction or
security case. It requires `signal-qa-1 → signal-qa-2` and
`signal-qa-2 → signal-qa-1` for protected text, multiline/UTF-8, encryption,
protected-composer binding, transcript overlay, burn, Covertext,
attachments/images, delivery/read receipts, reconnect, replay rejection,
malformed-data rejection, expiry, and window lifecycle.

Until the live signed Signal build yields reviewed accessibility selectors for
the exact destination, participant set, and composer, all 28 matrix stages are
`blockedUntilLiveAdapterReviewed`. Inventory and exact-window claim are the only
armable UIA actions. Their hash-pinned harness verifies the exact Signal
process/window class/title and OSL's fixed `Claimed` semantic status, but emits
only counts, geometry, and booleans. It does not return window titles or any UIA
content and does not change foreground focus. This is an intentional fail-closed
boundary, not a skipped test.

## Background screenshot boundary

Screenshots do not capture the desktop and do not require Signal or an RDP
window to be foregrounded. `PrintWindow` renders the exact hash-pinned OSL HWND;
the tool crops it to the top 48 title-bar pixels before persistence. All Signal,
transcript, composer, attachment, provider, and message regions are excluded by
shape. The crop is uploaded to a private blob through managed identity, removed
locally, and represented in output only by its SHA-256, dimensions, and fixed
safety booleans.

This evidence proves only background capture operation plus lifecycle/title-bar
chrome. It does not prove transcript, composer, provider, or message-surface
polish. The region must not be broadened without a separately reviewed mask
whose geometry proves every Signal and message-content pixel is excluded.
