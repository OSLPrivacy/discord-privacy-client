# oslprivacy-cipher-store

Cloudflare Worker + D1/R2 that stores short-TTL E2E ciphertext blobs
keyed by random 8-byte IDs. A database leak yields E2E-encrypted
payloads rather than plaintext, and the application schema records no
user identities. Cloudflare edge logs and short-lived hashed-IP rate-limit
keys remain part of the provider-side metadata exposure.

## Routes

| Method | Path                | Notes                                          |
|--------|---------------------|------------------------------------------------|
| GET    | `/v1/healthz`       | Liveness probe.                                |
| POST   | `/v1/blob`          | Body: ciphertext bytes. Requires `X-OSL-TTL-Seconds` ∈ {3600, 86400, 259200, 604800} and a 32-hex-character `X-OSL-Fetch-Token`. Returns `{ id, expires_at }`. |
| GET    | `/v1/blob/:id_hex`  | Requires the upload's fetch token. Returns raw ciphertext bytes, or 404 if missing / expired. |
| DELETE | `/v1/blob/:id_hex`  | Requires the upload's fetch token and burns the blob idempotently. |
| POST   | `/v1/attachment` | Streams already-sealed bytes to private R2. Same TTL/token headers; returns a 32-hex opaque ID. |
| POST   | `/v1/attachment/session` | Starts a multipart upload. Also requires `X-OSL-Size-Bytes` for the complete sealed object. |
| PUT    | `/v1/attachment/:id_hex/part/:number` | Streams one sealed part (1–65, at most 8 MiB) with the attachment token. |
| POST   | `/v1/attachment/:id_hex/complete` | Atomically completes a fully received multipart object. |
| GET    | `/v1/attachment/:id_hex` | Capability-gated streaming ciphertext response. |
| DELETE | `/v1/attachment/:id_hex` | Capability-gated, idempotent object burn. |
| POST   | `/v1/link`          | Create a view-once link. Requires an `OSL-Link-Grant` authorization, `X-OSL-TTL-Seconds: 3600`, and distinct 32-hex `X-OSL-Fetch-Token` / `X-OSL-Manage-Token`. Returns `{ id, expires_at }`. |
| POST   | `/v1/link/:id/status` | Sender-side status. Manage token in the JSON body. Returns `created` / `retrieved` / `expired`. |
| DELETE | `/v1/link/:id`      | Sender-side revoke. Manage token in the JSON body. |
| GET    | `/v/:id`            | View-once landing page. **Byte-identical for every id**, always 200. See below. |
| POST   | `/v/:id/fetch`      | Releases ciphertext. Fetch token in the JSON **body**, same-origin `Origin`, and `X-OSL-Gesture: 1`. |
| POST   | `/v/:id/burn`       | Best-effort early destroy from the landing page. Always 204. |
| GET    | `/robots.txt`       | `Disallow: /`. |

## View-once links for non-OSL recipients

A recipient with no OSL and no account opens a link, sees the content
once, and it is gone. This lane is **structurally weaker than
OSL-to-OSL and always will be**: the strong version needs a native
protected surface, and a browser cannot have one.

**Key custody.** The AES-256-GCM key is generated by the OSL client and
placed in the URL **fragment** (`#k=…&t=…`). Browsers do not transmit
fragments — not in the request line, not in `Referer`, not across
redirects. The Worker stores ciphertext plus SHA-256 digests of two
bearer capabilities, and has no column, parameter or code path that
could hold a key. AES-256-GCM specifically, so the browser decrypts with
native WebCrypto and the page ships zero JS crypto.

**No existence oracle.** `GET /v/<id>` returns the same static bytes,
the same `Content-Length` and the same `ETag` with status 200 for every
id — live, expired, already retrieved, or never created. The page embeds
no id; it reads one from `location.pathname` at runtime.

**A crawler cannot burn a view.** Ciphertext moves only on
`POST /v/<id>/fetch`, which needs the capability in the request body, a
same-origin `Origin`, and a header the page sets only after an
`isTrusted` `pointerdown`/`keydown` on the reveal button. A crawler that
executes the JS still cannot click. OSL additionally posts the URL
wrapped in angle brackets (`<https://…>`), Discord's documented
suppression for embed generation.

**The burn is not on fetch.** The first successful fetch sets
`reserved_until = now + 60s` and returns the bytes; repeat fetches
inside that window are idempotent, so a flaky network cannot destroy
content the recipient never saw. At `reserved_until` the ciphertext is
destroyed regardless of client confirmation. The enforceable claim is
exactly **"the link dies after one view, or 60 seconds, whichever is
first."**

**Screenshots are not prevented.** There is no web API for it. The only
real mechanism is EME/DRM, which is ruled out, and `org.w3.clearkey`
carries no robustness guarantee so browsers do not mark the surface
protected. Everything the page does — blank-and-burn on
`visibilitychange`/`blur`, `PrintScreen` `keyup`, canvas-only rendering
with no image element and no object URL, suppressed right-click / drag /
selection / copy — is **deterrence**, and the page says so in those
words. There is deliberately **no DevTools detection**: it is theatre,
false-positives constantly, and breaks accessibility tooling. Temporal
slicing ships **off by default**, labelled experimental, force-disabled
under `prefers-reduced-motion: reduce`, and behind a photosensitive-
seizure warning — it leaks a large fraction of the image per still
capture, is defeated outright by any screen recorder, and a large
high-contrast field flashing above 3 Hz is a WCAG 2.3.1 hazard.

**Sender-facing vocabulary.** `Link created`, `Retrieved at HH:MM`,
`Expired without being retrieved`. Never "read", "seen" or "viewed" —
retrieval is not viewing. The exact wording, including the pre-send
warning, lives in `crates/crypto/src/view_once_link.rs` and is pinned by
test.

### Domain and abuse posture

**One neutral, unremarkable, aged domain.** Rotating fleets were
considered and rejected: they are correlatable through public
Certificate Transparency logs, passive DNS and shared origin, and they
are the textbook phishing/C2 signature — risking Safe Browsing flags,
Discord's link filter blocking the URL outright, and registrar or
Cloudflare enforcement against the *account*, which would take down the
cipher-store and keyserver the strong lane depends on. Per-link variety
comes from the 16-byte random path id, and optionally from random
subdomains under a single wildcard certificate.

**Creation is restricted to authenticated OSL clients** and fails closed
when it cannot be: without `LINK_GRANT_PUBKEY_B64` the Worker refuses
`POST /v1/link` with 503. An ungated one-time link store is an open,
logless, self-deleting file host — a malware distribution service — and
that is what gets a domain and an account taken down. A grant is
anonymous by design (`aud`/`exp`/`jti` only, single-use, ≤10 min), so
the cipher-store never learns who created a link; enforcement handles
live at the keyserver, which already knows identities.

**Abuse path:** `abuse@<link host>`, published on every landing page.
The mailbox must exist before the route is enabled.

## Limits

- Max blob size: **64 KB**. Typical v=4 wire ciphertexts are ~1–2 KB.
- Direct uploads remain capped at **26 MiB**. Multipart uploads support a **512 MiB plaintext** file with a bounded framing allowance (**513 MiB sealed**, 65 parts of at most 8 MiB).
- D1 stores only opaque object/part/expiry state and SHA-256 capability digests, never raw bearer tokens. Atomic conditional inserts cap live attachment metadata at 512 rows and 8 GiB of declared sealed bytes.
- TTL values: 1h, 24h, 72h, or 7d. No other values accepted. View-once links accept **only** 1h, so the sender warning's "after 1 hour" is literally true.
- Max view-once link payload: **256 KiB** sealed. Larger images must be downscaled client-side.
- Best-effort KV rate limits per IP per hour: 600 uploads / 3600 fetches / 600 deletes. Identifiers are HMAC-pseudonymized with a Worker secret. KV is eventually consistent; limiter failures deny anonymous writes while reads remain available.
- Attachment transport uses separate budgets: 140 upload/session/part requests, 120 fetches, and 60 deletes per IP per hour.
- View-once links use dedicated budgets well below the generic ones: **120 creations and 120 retrievals** per IP per hour. A link is meant to be opened once, by one person, from one browser.

## Data-minimisation posture

- **No identity binding.** Uploads carry no user ID or account credential. The opaque fetch token separates a bare blob ID from fetch/delete authority, but it is not proof of identity, sender authenticity, or conversation membership.
- **No variable application logging.** Fixed failure event names contain no
  identifiers, URLs, sizes, row counts, or timing details; sweep volume is not
  logged.
- **TLS-terminator logs** (Cloudflare edge) are out of our control. Onion-routing the client side is a Phase 6+ research item.
- **Cleanup cron** runs every 5 minutes and deletes expired rows. For view-once links it also destroys the ciphertext of any link past its reservation window or its TTL, regardless of client confirmation, and purges the content-free receipt a day after expiry.
- **View-once links record no IP, user agent, referrer or timing.** The entire retrieval record is `retrieved_at` at second granularity plus a small integer count.
- Attachment cleanup claims at most 100 expired objects per invocation through
  migration `0008`'s D1 companion table. Each claim is bound to a random Worker
  identity and token, fenced by a monotonic lease version, and recoverable after
  a two-minute lease. R2 cleanup remains first and idempotent; only the exact
  live claim may then delete metadata. A failed object keeps its indexed row,
  receives bounded retry backoff, and does not prevent unrelated claims from
  running. The previous Worker ignores the additive claim table, while the
  matching Worker refuses before any sweep mutation if the table is absent.
